# Accessibility

Saans is built to WCAG 2.2 level AA. Each criterion below names how the app meets it, where, and
the automated test that holds it, so the claim is checked on every `npm run verify` and in CI
rather than asserted once.

## What is tested, and how

- **axe-core** runs on every component in its main states (empty, filled, field error, request
  failed, plan shown, answer shown) and on the whole page with a place, a forecast and a finished
  plan on screen: the `*.test.ts` file beside each component, and
  [a11y.test.ts](web/src/a11y.test.ts).
- **Structure** is asserted on the rendered page and the shipped `index.html`: one `h1`, no
  skipped heading level, one header, main and footer, a skip link that lands on a focusable
  target, unique ids, every label and ARIA reference resolving, native controls only, no
  placeholders: [a11y.test.ts](web/src/a11y.test.ts).
- **Stylesheet rules** that jsdom cannot lay out are asserted from the shipped CSS: the focus
  ring, target sizes, relative font sizes, no fixed widths, motion only when welcome, forced
  colours, nothing sticky: [a11y.test.ts](web/src/a11y.test.ts).
- **Contrast** is computed from the colour tokens of the real stylesheet for both themes, because
  axe cannot decide contrast without layout: [contrast.test.ts](web/src/contrast.test.ts).
- **Behaviour** (focus moves, live regions, field errors, busy buttons) is asserted in the
  component tests named in the table.

## Design decisions

- **The chart is never the only way in.** The 48-hour forecast is given three times: a sentence
  that names the cleanest and the most polluted hour, the bars with a time axis and a key that
  names each colour, and a table of every hour. The table is always on screen, in a region that
  scrolls and takes keyboard focus, so nobody has to find and open a disclosure to get the data.
- **`aria-disabled`, not `disabled`, on busy buttons.** While a request runs the button stays
  focusable, announces its state and ignores further presses. A `disabled` button would drop out
  of the tab order under the finger of someone who had just pressed it.
- **Corrections are explained, not silent.** A household count outside the accepted range is
  corrected to the nearest valid value, and the field says what it was changed to and why.
- **Announcements sit outside busy regions.** The plan section is `aria-busy` while Gemini writes,
  so its status line lives outside it and is read at once; the finished plan takes focus rather
  than being read out whole as a live region.
- **Themes, forced colours and motion.** Light and dark follow the system setting and pass the
  same contrast tests. Under `forced-colors: active` the bars use system colours and the colour
  key steps aside for the table. Nothing moves unless the system has no reduced-motion preference.
- **No JavaScript, no silence.** A `noscript` note says the page needs JavaScript to load live air
  data and the plan.

## Limits of this evidence

The tests run in jsdom, which has no layout engine and no screen reader. Reflow, target size and
focus visibility are therefore asserted from the stylesheet's rules, and announcements from the
roles and live regions in the markup. Before a release I also check the page by hand in a browser
at 390 px wide and at 200 % zoom in both themes; that check is not part of `npm run verify`, and
no session with a real screen reader is claimed here.
